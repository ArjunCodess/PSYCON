# Week 5: group recording, psychologist marksheets, and evidence backed model training
## Summary
Build a web app where an operator uploads **one video of a group discussion**, creates up to ten participant slots, and assigns each visible student a stable `Participant 1`, `Participant 2`, and so on. A psychologist opens each participant’s slot, watches the relevant recording, and enters the 20 answers from the [current marksheet](/C:/Users/USER/Desktop/code/PSYCON/docs/PSYCON_Psychologist_Observation_Mark_Sheet.pdf). PSYCON then learns to predict those answers and links each prediction to the moments that support it.
The uploaded video is assumed to contain its original audio track. The device in the centre of the table is treated as a **shared microphone**, not as a source of individual physiology. All participants can have recording based profiles; none receives an individual wrist or physiological score from that shared device.
This changes Week 5’s target. The existing binary stress comparison in `research/evaluation.py` cannot train the current 0–4 marksheet as written. Keep that earlier research path identifiable, but build a separate, versioned group observation pipeline.
## Collection and input workflow
1. **Set up the session.** The operator enters a session ID, date, class and section, topic, language, moderator, camera position, recording start time, and consent status. Require one recording and between two and ten participant slots. Store names and signatures only with the restricted consent record; use anonymous participant codes throughout annotation and training.
2. **Upload the video.** Accept an approved video format with an audio track, validate duration, codecs, dimensions, size, and readable timestamps, then store the original file in the protected object store with its SHA-256 hash. Extract working audio, frames, and thumbnails through a background job. Do not use the existing audio demo upload route for this; it has a five minute, 12 MB limit and is explicitly a local demo.
3. **Assign people.** Show a frame where all students are visible. The operator marks each seat from the **right side of the displayed image toward the left**, assigns `Participant 1`, `Participant 2`, and so on, and confirms the assignment. Save the marked frame, each seat region, and the camera orientation. If seats overlap or someone leaves the frame, the operator can correct the region over a time interval. These numbers are session labels, not identities inferred from appearance.
4. **Align voices.** Run diarization and show anonymous voice clusters with short playable examples. The operator maps each cluster to a participant slot using visible speaking moments; allow `unknown`, multiple uncertain turns, and later corrections. Never silently equate `Speaker 1` with `Participant 1`. Preserve overlap and the original cluster assignment for audit.
5. **Enter marksheets in the web app.** Each participant page has synchronized video playback, a transcript and speaker timeline, and items A–T with buttons `0`, `1`, `2`, `3`, `4`, and `N/O`. Selecting a score above zero requires at least one timestamped evidence interval and a short description of the preceding event and observed response. Items Q–T additionally require a same participant baseline interval and an identifiable trigger. A zero requires a fair opportunity; `N/O` requires a reason such as no opportunity, poor recording, or uncertain speaker identity. Save drafts automatically and require an explicit psychologist submission.
6. **Support file attachment.** Add an optional PDF upload inside each participant’s slot so an already completed paper marksheet can be kept with that participant. The psychologist still confirms the 20 answers in the digital form. Do not use unverified PDF text extraction as training labels. Display the attached sheet beside the entered answers for review.
7. **Review.** Support a second psychologist independently rating a chosen subset without seeing the first ratings. Show disagreements item by item, retain both originals, and create a separately recorded adjudicated answer. Record rater code, marksheet version, submission time, changes, reviewer, and reason for each correction.
## Data and service design
Extend the existing Flask, PostgreSQL, worker, and object storage stack. Add `group_sessions`, `group_participants`, `recordings`, `seat_assignments`, `speaker_turns`, `speaker_mappings`, `marksheets`, `item_ratings`, `evidence_intervals`, `reviews`, and `model_predictions`. Use foreign keys so one group session owns one recording and many participant slots, and each submitted marksheet belongs to exactly one slot and one rater. Keep the existing device sessions compatible; do not force the group recording into the current `sessions.participant_id` column, which allows only one participant.
Expose authenticated operator and psychologist workflows through routes such as:
- `POST /api/v1/group-sessions`, `GET /api/v1/group-sessions/{id}`
- `POST /api/v1/group-sessions/{id}/recording`, plus processing status and a restricted playback endpoint
- `PUT /api/v1/group-sessions/{id}/participants` for seat order and participant codes
- `PUT /api/v1/group-sessions/{id}/speaker-mappings` for reviewed voice assignments
- `GET/PUT /api/v1/group-sessions/{id}/participants/{participant_id}/marksheets/{rater_id}` for drafts
- `POST .../submit`, `POST .../review`, and `POST .../attachments`
- `GET /api/v1/group-sessions/{id}/export` for a versioned research package
Create distinct operator, psychologist, and reviewer permissions. Use named accounts rather than a shared operator token for ratings. Audit access to recordings, changes to participant mapping, mark submissions, exports, and deletion. Keep raw video, audio, transcripts, attached PDFs, and signatures out of Git and routine logs. Withdrawal must remove a participant’s labels and derived data from future dataset versions; a group recording also contains peers, so its retention or redaction decision must follow the approved session protocol.
The training record for each answer must include `group_session_id`, anonymous `participant_id`, `rater_id`, marksheet version, item letter, score or `N/O`, evidence start and end times, context note, baseline and trigger intervals when required, quality state, and source recording hash. Save model predictions in separate tables; never overwrite psychologist ratings.
## Training and interpretation
Implement this as a staged pipeline so useful parts work before enough real data exist to train a model:
1. **Processing baseline.** Extract the audio track, timestamped transcript, diarized turns, overlap, speaking duration, pauses, and recording quality. Add video frame sampling and seat visibility checks. Reuse the existing audio analysis where its input and quality rules fit; add video processing as a new component. All derived records retain source hashes, time offsets, tool versions, and failure reasons.
2. **Human verified identities.** Use the seat and speaker mappings confirmed in the app to associate turns and visible events with participant slots. Unknown or conflicting assignments stay unknown. A prediction tied to the wrong person counts as a failure even if its description sounds plausible.
3. **Training examples.** Build one supervised example per participant, item, and rated session, with the relevant evidence intervals and enough preceding context. Keep the full session score distinct from event level evidence: a timestamp supports the psychologist’s answer but does not turn the entire recording into many independent labels. Never convert `N/O` to zero, infer a condition label, or manufacture missing scores.
4. **First model.** Start with reproducible feature and text baselines for the 20 ordinal answers, alongside a simple frequency baseline. Use video features only for items that genuinely need visible behaviour, audio and transcript features for speech items, and combined evidence where both are available. Predict the five score levels and an abstention or insufficient evidence state per item. Generate the written account from a constrained template populated with verified timestamps, context, observed action, score, and confidence. This prevents a fluent free text model from inventing events.
5. **Session interpretation.** Apply the [interpretation guide](/C:/Users/USER/Desktop/code/PSYCON/docs/PSYCON_Tendency_Flag_Guide.pdf): scores 0–1 do not establish a session pattern, 2 calls for more evidence, and 3–4 can appear in a session summary only with cited moments. Q–T need a same person baseline and an identifiable trigger. Show the psychologist’s answer and the model’s answer separately, with a way to correct speaker identity, timestamps, and item evidence.
6. **Split and evaluate correctly.** Because one recording contains several participants, keep **the entire group session in one data split**. If a participant appears in multiple sessions, keep all their sessions in that same split too; form connected groups from shared sessions and repeat participants before assigning train, validation, and test. Report per item coverage, exact and within one point agreement, mean absolute error, weighted kappa, evidence interval accuracy, speaker mapping error, and abstention rate. Review errors by participant speaking opportunity, language, topic, overlap, seat visibility, and recording quality. Freeze splits and scoring rules before examining test results.
7. **Data sufficiency gate.** If there are too few independent sessions or too few nonzero examples for an item, show human ratings and descriptive results only; mark that model item unavailable. A successful software pipeline is not a validated model result. Store dataset manifest, recording hashes, consent version, marksheet version, model version, code revision, split assignment, and evaluation results for every run.
